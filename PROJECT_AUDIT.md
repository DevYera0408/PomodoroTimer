# Технический аудит проекта

## 1. Общая информация о проекте

**Назначение проекта.**
Веб-приложение «Фокус» — таймер Pomodoro с управлением задачами и учётом дневного прогресса. Ориентировано на студентов. Интерфейс на русском языке. Бэкенда, аккаунтов и внешних API нет: все данные хранятся в `localStorage` браузера.

**Фактически обнаруженный технологический стек.**
- React 19 (`react`, `react-dom`) + React StrictMode (`React.StrictMode` в `src/main.tsx`).
- Vite 8 (`vite`, `@vitejs/plugin-react`) как сборщик и dev-сервер (порт 8443).
- TypeScript 5.7 в строгом режиме (`strict: true`) — см. `tsconfig.json`.
- Tailwind CSS v4 через плагин `@tailwindcss/vite` (без `tailwind.config` и `postcss`).
- Пакетный менеджер pnpm, Node 22.
- Форматтер `oxfmt`.
- Плагины Figma Make в `vite.config.ts` (генерация `robots.txt`, реплей оверлея ошибок, fallback для React Refresh, dev-страница `/.figma/make/kit.html`).

Фактически установленные зависимости соответствуют `AGENTS.md`. Отсутствуют Zustand, Framer Motion, lucide-react и роутер — это заявлено и подтверждено кодом.

**Основные компоненты и их взаимосвязи.**
- `src/main.tsx` — точка входа: монтирует `<App />` в `#root` внутри `React.StrictMode`, подключает `./index.css`.
- `src/App.tsx` — вся логика приложения (313 строк): типы `Mode`, `Task`, `DailyStats`; константа `DURATIONS`; хелперы `dateKey`, `readTasks`, `readStats`, `playBeep`; иконки `TrashIcon`, `ThemeIcon`; компонент `App`.
- `src/index.css` — подключение Tailwind, кастомный вариант `dark`, классы `.card`, `.primary-button`, `.secondary-button`, `.icon-button`, `.add-button`, `.task-input`, `.task-row`, `.task-checkbox`, `.delete-button`, `.mode-indicator`, `.animate-task-in` и `@keyframes task-in`.
- `index.html` — HTML-оболочка со слотами комментариев `figma:*`, заполняемыми плагином.
- `vite.config.ts` — конфигурация сборки и плагины Figma.
- `docs/ai-memory/*.md` — общая память проекта (все четыре файла пусты).
- Соответствие между `DURATIONS` (`work` 25 мин / `rest` 5 мин) и логикой таймера; между формой `Task`/`DailyStats` и ключами `localStorage` (`focus-tasks`, `focus-stats`, `focus-theme`).

**Область проведённого анализа.**
Прочитаны и проанализированы: `src/App.tsx`, `src/main.tsx`, `src/index.css`, `src/vite-env.d.ts`, `index.html`, `package.json`, `tsconfig.json`, `vite.config.ts`, `.figma/make/site.json`, `AGENTS.md`, `CLAUDE.md`, `.gitignore`, а также файлы `docs/ai-memory/`. Каталог `node_modules` и lockfile детально не разбирались (только подтверждено наличие зависимостей). Аудит носит исключительно статический характер (чтение исходного кода); приложение не запускалось.

## 4. Проблемы высокого приоритета

### BUG-001. Побочные эффекты внутри апдейтера `setSeconds` приводят к двойному звуку и завышению времени фокуса

1. **ID:** BUG-001
2. **Краткость:** Побочные эффекты в апдейтере состояния таймера.
3. **Severity:** Высокая.
4. **Расположение:** `src/App.tsx`, строки 109–125 (особенно 112–118: `playBeep()` вызов на строке 114, `setStats(...)` на строке 116), внутри обработчика `setSeconds`.
5. **Описание некорректного поведения.** При достижении нуля в режиме «Работа» вызываются `playBeep()` и `setStats` внутри функции-апдейтера `setSeconds`. В React StrictMode (подключён в `src/main.tsx:7`) апдейтеры намеренно вызываются дважды для проверки чистоты. В результате звуковой сигнал воспроизводится дважды, а `focusMinutes` увеличивается на 50 вместо 25 за одну завершённую рабочую сессию.
6. **Первопричина (по коду).** Нарушено требование чистоты апдейтера: `setSeconds((value) => { ... playBeep(); setStats(...); ... })` содержит побочные эффекты и вложенный `setState`. React вызывает апдейтеры многократно (в dev — дважды), поэтому эффекты дублируются.
7. **Условия воспроизведения.** Режим разработки (`pnpm dev`) + React StrictMode; дождаться перехода таймера из «Работа» в «Отдых». Эффект стабилен.
8. **Ожидаемое / фактическое.** Ожидается один звук и рост `focusMinutes` на 25 за сессию. Фактически в dev-режиме — двойной звук и +50.
9. **Влияние.** Искажает дневную статистику «Время фокуса сегодня» и создаёт избыточный звук. В production-сборке двойной вызов StrictMode отсутствует, но сам паттерн (сайд-эффекты в апдейтере) остаётся источником риска при конкурентных перерисовках.
10. **Безопасная проверка.** Статически: см. `src/App.tsx:112-121` и `src/main.tsx:7`. Рантайм-проверка (запуск dev) не выполнялась в рамках аудита.
11. **Рекомендуемое направление исправления.** Вынести побочные эффекты из апдейтера: вычислять границу сессии во внешней функции/эффекте, отдельно вызывать `playBeep()` и обновлять `stats` вне апдейтера `setSeconds`.

## 5. Проблемы среднего приоритета

### BUG-002. `readTasks` не проверяет, что распарсенные данные — массив, что приводит к падению приложения

1. **ID:** BUG-002
2. **Краткость:** Отсутствует валидация формы данных из `localStorage` при чтении задач.
3. **Severity:** Средняя (потенциально высокая — приводит к «белому экрану» без error boundary).
4. **Расположение:** `src/App.tsx`, строки 15–21 (`readTasks`), использование в 72, 127–131 и 261.
5. **Описание некорректного поведения.** `readTasks` возвращает результат `JSON.parse(...)` без проверки `Array.isArray`. Если в `focus-tasks` лежит валидный JSON, но не массив (`"null"` → `null`, `"{}"` → объект), функция вернёт `null`/объект, вопреки декларированному типу `Task[]`. Далее `tasks.filter` (строка 128) или `tasks.map` (строка 261) выбросят `TypeError`, компонент падает, и всё приложение размонтируется (error boundary отсутствует).
6. **Первопричина (по коду).** `try { return JSON.parse(...) } catch { return [] }` защищает только от ошибок парсинга, но не от неверной структуры. Аннотация возвращаемого типа `(): Task[]` не соответствует рантайм-поведению.
7. **Условия воспроизведения.** Наличие в `localStorage['focus-tasks']` строки `null` или `{}` (например, из-за ручного изменения, старой версии приложения или частичной записи) и последующая загрузка страницы.
8. **Ожидаемое / фактическое.** Ожидается безопасный возврат `[]` при некорректных данных. Фактически — исключение и падение UI.
9. **Влияние.** Полная неработоспособность интерфейса при повреждённых/устаревших данных tasks.
10. **Безопасная проверка.** Статически: `src/App.tsx:15-21,128,261`. Рантайм не воспроизводился.
11. **Рекомендуемое направление исправления.** Валидировать результат: проверять `Array.isArray(parsed)` и при необходимости проверять поля элементов (`id`, `text`, `completed`); возвращать `[]` при несоответствии.

### BUG-003. Запись в `localStorage` не обёрнута в try/catch, что противоречит заявленной конвенции и может уронить приложение

1. **ID:** BUG-003
2. **Краткость:** Необработанные исключения при записи в `localStorage`.
3. **Severity:** Средняя.
4. **Расположение:** `src/App.tsx`, строки 83–94 (`setItem` для `focus-tasks`, `focus-stats`, `focus-theme`); инициализация темы на строке 79.
5. **Описание некорректного поведения.** Чтение защищено `try/catch` (строки 16–20, 24–29), однако записи `localStorage.setItem(...)` выполняются без обработки исключений. При режиме приватного просмотра, отключённом хранилище или превышении квоты `setItem` выбрасывает исключение; ошибка в `useEffect` не перехватывается и приводит к размонтированию дерева (белый экран).
6. **Первопричина (по коду).** Асимметрия обработки: чтение защищено, запись — нет; при этом `AGENTS.md` требует обрабатывать `localStorage` в try/catch.
7. **Условия воспроизведения.** Среда, в которой запись в `localStorage` недоступна или превышен лимит, при любом изменении задач/статистики/темы.
8. **Ожидаемое / фактическое.** Ожидается устойчивая работа при недоступной записи. Фактически — возможное исключение и падение.
9. **Влияние.** Потеря работоспособности приложения в ограниченных окружениях.
10. **Безопасная проверка.** Статически: `src/App.tsx:79,83-94`. Рантайм не воспроизводился.
11. **Рекомендуемое направление исправления.** Обернуть все вызовы `setItem` и чтение темы в `try/catch` (по аналогии с `readTasks`/`readStats`).

### BUG-004. Прогресс и текст «Выполнено сегодня» смешивают задачи за сегодня и общее число всех задач

1. **ID:** BUG-004
2. **Краткость:** Несогласованный числитель и знаменатель прогресса.
3. **Severity:** Средняя.
4. **Расположение:** `src/App.tsx`, строки 127–131 (`completed`, `progress`) и 296 (`Выполнено сегодня: {completed} из {tasks.length} задач`).
5. **Описание некорректного поведения.** Числитель `completed` считает только задачи с `completedDate === today`, а знаменатель — все задачи `tasks.length` (без привязки к дате). Если в списке остались задачи, завершённые в прошлые дни (их `completedDate` ≠ сегодня), они попадают в знаменатель, но не в числитель. Прогресс и текст становятся некорректными: даже при завершении всех задач «на сегодня» процент не достигает 100%.
6. **Первопричина (по коду).** В приложении нет понятия «задачи за сегодня»; знаменатель использует общее число задач, а числитель фильтруется по дате.
7. **Условия воспроизведения.** Добавить задачи, отметить часть из них, затем сменить дату (или данные `completedDate` в прошлом), оставив задачи в списке.
8. **Ожидаемое / фактическое.** Ожидается согласованный расчёт (либо все задачи, либо задачи за сегодня в обоих местах). Фактически — несогласованные показатели.
9. **Влияние.** Вводит пользователя в заблуждение относительно прогресса; полоса `role="progressbar"` (`aria-valuenow`) передаёт неверное значение.
10. **Безопасная проверка.** Статически: `src/App.tsx:127-131,296,307`. Указано в `AGENTS.md` как известная проблема.
11. **Рекомендуемое направление исправления.** Согласовать логику: либо считать «задачи за сегодня» для обоих показателей, либо явно разделить «выполнено сегодня» и «всего задач».

### BUG-008. `crypto.randomUUID()` недоступен в небезопасном контексте

1. **ID:** BUG-008
2. **Краткость:** Зависимость добавления задачи от secure context.

4. **Расположение:** `src/App.tsx:148` (`id: crypto.randomUUID()`).

7. **Условия воспроизведения.** Доступ к приложению по HTTP через IP (не localhost) в браузере без `crypto.randomUUID`.
8. **Ожидаемое / фактическое.** Ожидается генерация уникального id с фолбэком. Фактически — возможное исключение.
9. **Влияние.** Не работает добавление задач в небезопасном контексте.
10. **Безопасная проверка.** Статически: `src/App.tsx:148`, `vite.config.ts:34-35`. Требуется проверка способа доступа (localhost vs IP).
11. **Рекомендуемое направление исправления.** Добавить резервный генератор id при отсутствии `crypto.randomUUID`.

## 7. Подозрительные места, требующие проверки

### SUSP-001. Гонка на границе суток между `stats.date` и `dateKey()` в момент отметки задачи

- **Почему выглядит проблемно:** `today` вычисляется как `stats.date` (`src/App.tsx:81`), который обновляется только эффектом `checkDay` раз в 60 секунд или по событию `focus` (`src/App.tsx:96-107`). При этом `toggleTask` присваивает `completedDate: dateKey()` (`src/App.tsx:163`), а фильтр `completed` сравнивает с `today` (`src/App.tsx:128`). Если таймер или пользователь пересекает полночь до срабатывания `checkDay`, задача помечается датой нового дня, но `today` ещё равна вчерашней — задача не попадёт в счётчик, а при последующем сбросе статистики `focusMinutes` может обнулиться уже после начисления.
- **Доступные доказательства:** использование двух разных источников «сегодняшней» даты (`stats.date` и `dateKey()`), отложенное обновление `stats.date`.
- **Необходимая проверка:** смоделировать переход через полночь (или временно изменить системные часы) и наблюдать согласованность `completed` и `stats`.
- **Почему не подтверждено:** требуется наблюдение рантайма на стыке суток; статически лишь видна потенциальная рассинхронизация.

### SUSP-002. `readStats` не валидирует форму и тип `focusMinutes`

- **Почему выглядит проблемно:** `readStats` возвращает сохранённый объект, если `saved.date === dateKey()`, без проверки наличия/типа `focusMinutes` (`src/App.tsx:23-31`). При повреждённом значении (например, `focusMinutes` — строка) операция `current.focusMinutes + 25` (строка 116) даст конкатенацию строк, а не сумму.
- **Доступные доказательства:** отсутствие проверок полей; арифметическое использование без приведения типов.
- **Необходимая проверка:** записать в `focus-stats` некорректное значение и проверить отображение/начисление.
- **Почему не подтверждено:** требует повреждённых данных; при корректных данных не проявляется.

### SUSP-003. Замыкание `mode` внутри интервала и повторный вызов апдейтера в production

- **Почему выглядит проблемно:** апдейтер `setSeconds` читает `mode` из замыкания эффекта (`src/App.tsx:112-121`), а эффект пересоздаётся на смену `mode` (`src/App.tsx:125`). Дополнительно React 19 может повторно вызывать апдейтеры при конкурентных перерисовках, из-за чего побочные эффекты (см. BUG-001) теоретически дублируются и в production.
- **Доступные доказательства:** побочные эффекты внутри апдейтера; зависимость эффекта от `mode`.
- **Необходимая проверка:** сборка production и стресс-тест переключения режимов/паузы.
- **Почему не подтверждено:** гарантированное двойное исполнение апдейтеров в production не задокументировано; требуется рантайм-проверка.

### SUSP-004. Чтение темы из `localStorage` в инициализаторе `useState` без try/catch

- **Почему выглядит проблемно:** `useState(() => localStorage.getItem('focus-theme') === 'dark')` (`src/App.tsx:79`) выполняется на этапе инициализации; при недоступном хранилище (исключение при доступе к `localStorage`) это приведёт к падению до монтирования.
- **Доступные доказательства:** отсутствие обработки исключений, в отличие от `readTasks`/`readStats`.
- **Необходимая проверка:** запуск в окружении с отключённым/заблокированным `localStorage`.
- **Почему не подтверждено:** зависит от конкретной среды; доступ к `localStorage` обычно не бросает исключение.

## 8. Анализ основных пользовательских сценариев

1. **Инициализация приложения.** `main.tsx` → `App`. Начальное состояние читается из `localStorage` (`readTasks`, `readStats`, тема). Эффекты записывают состояние обратно при каждом изменении. Проверено статически; отмеченные риски — BUG-002 (форма данных), BUG-003/SUSP-004 (обработка ошибок хранилища).
2. **Таймер (старт/пауза/сброс).** Кнопка `Старт/Пауза` (`setRunning`), `Сброс` обнуляет `seconds` и останавливает таймер. Интервал раз в секунду уменьшает `seconds`; при нуле — сигнал и переключение режима (`work`↔`rest`). Выявлен BUG-001 (сайд-эффекты в апдейтере), SUSP-003 (замыкание `mode`), а также известный дрейф `setInterval` в фоне (описан в `AGENTS.md` — не подтверждался рантайм).
3. **Переключение режима вручную.** `chooseMode` устанавливает режим, сбрасывает `seconds` и останавливает таймер; визуальный индикатор смещается через `translate-x-full`. Логика согласована.
4. **Управление задачами.** Добавление (Enter или кнопка), проверка непустой строки, анимация `animate-task-in`; отметка чекбоксом обновляет `completed` и `completedDate`; удаление фильтрует массив. Отмечены BUG-004 (прогресс), BUG-008 (`crypto.randomUUID`), SUSP-001 (граница суток).
5. **Прогресс за сегодня.** Выводит `completed`, `focusMinutes` и полосу `role="progressbar"`. Отмечен BUG-004.
6. **Тема.** Переключатель меняет класс `dark` на `<html>` и сохраняет выбор. Логика согласована; риск при недоступном хранилище (SUSP-004).
7. **Смена суток.** `checkDay` сбрасывает `focusMinutes` при смене `dateKey()`. Отмечен SUSP-001.

**Что не удалось проверить:** фактическое поведение таймера в фоновой вкладке, воспроизведение двойного сигнала в dev, поведение при повреждённых данных `localStorage`, работу звука в разных браузерах, доступность по IP-over-HTTP — всё это требует запуска приложения, что выходило за рамки статического аудита.

## 10. Ограничения аудита

- **Компоненты/файлы, недоступные для анализа:** отсутствуют среди исходников. Каталог `node_modules` и файл `pnpm-lock.yaml` детально не разбирались (только подтверждено наличие зависимостей); плагины Figma в `vite.config.ts` — сторонний сгенерированный код, не являющийся частью бизнес-логики.
- **Тесты не запускались:** в проекте отсутствуют тестовые файлы (по результатам поиска); запуск тестов не производился.
- **Рантайм не проверялся:** приложение не запускалось (dev/build/typecheck не выполнялись в рамках аудита); поведение, зависящее от браузера, времени, фоновых вкладок и `localStorage`, оценено статически.
- **Выводы основаны на статическом анализе:** все находки получены чтением кода; часть из них (BUG-008, BUG-007, SUSP-001…004) требуют рантайм-подтверждения.
- **Документация памяти пуста:** файлы `docs/ai-memory/PROJECT.md`, `CURRENT_STATE.md`, `SESSION_LOG.md`, `DECISIONS.md` имеют нулевой размер, хотя `AGENTS.md` описывает их как источник контекста. Это ограничивает сверку кода с заявленным состоянием проекта.
- **Отсутствие error boundary:** влияет на оценку серьёзности падений (BUG-002, BUG-003) — любая необработанная ошибка приводит к полному «белому экрану», что учтено в оценках.
- **Вне области аудита:** вопросы безопасности (согласно требованиям) не рассматривались.
