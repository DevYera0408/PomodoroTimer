# Решения

## D-001 — Внешний вид: строгая чёрно-белая тема (2026-10-17)
- Контекст: интерфейс выглядел как сгенерированный ИИ (градиенты, индиго/синие цвета, крупные скругления, тени, шрифт Inter по умолчанию).
- Решение: палитра только чёрный/белый; светлая тема — фон `#FAF8F5`, текст/акцент `#1A1A1A`; тёмная — фон `#000000`, текст/акцент `#FFFFFF`. Активные элементы: светлая — чёрная заливка + белый текст, тёмная — белая заливка + чёрный текст.
- Форма: радиус ≤ 4px, вместо теней — границы 1px; крупные кнопки (`min-height: 3.25rem`).
- Шрифты: `IBM Plex Sans` (интерфейс), `IBM Plex Mono` (цифры таймера).
- Причины: убрать «шаблонный» вид, повысить читаемость и контраст, единый вид в обеих темах.
- Следствие: шрифты тянутся через Google Fonts `<link>`; при отсутствии сети работает фолбэк `system-ui`/`ui-monospace`.

## D-002 — Серия дней: вычисление из истории, а не инкрементальный счётчик (2026-10-17)
- Контекст: нужна серия (streak) с порогом 60 минут в день, сбросом при пропуске дня и сохранением рекорда.
- Решение: хранить историю минут по дням (`focus-days`) и выводить текущую серию из неё (`computeStreak`: последовательные засчитанные дни, заканчивая сегодня или вчера). `best` хранится отдельно в `focus-streak` и только растёт.
- Причины: устойчивость к StrictMode и повторным загрузкам (нет двойного инкремента), корректный сброс при пропущенном дне без отдельного «обнуляющего» кода.
- Следствие: минуты привязываются к дню начала сессии (`sessionDayRef`); `focus-stats` остаётся дневным счётчиком для отображения.

## D-003 — Каркас бэкенда: отдельный пакет `server/`, Fastify + TS strict (2026-10-20)
- Контекст: этап 1 из `docs/backend-foundation.md` — нужен минимальный каркас с `GET /api/v1/health`, чтобы разблокировать этап 2 (CRUD задач).
- Решение: отдельный приватный пакет `server/` со своими зависимостями и своим `tsconfig.json` (strict, NodeNext); сервер — Fastify 5 на Node 22, порт из `PORT` (дефолт 3000). БД и Prisma, а также CORS/rate-limit/auth/Docker отложены до этапа 3 и далее.
- Причины: минимум зависимостей и кода на старте; этап 2 можно делать без выбора хостинга БД; клиент остаётся нетронутым (его `package.json` и lockfile не меняются), пакеты изолированы.
- Следствие: `server/pnpm-lock.yaml` — отдельный; сборка кладёт артефакты в `server/dist`. Postinstall у `esbuild` (зависимость `tsx`) не разрешён — `pnpm install` пишет `ERR_PNPM_IGNORED_BUILDS`, но `tsx`/`dev` и сборка работают.
